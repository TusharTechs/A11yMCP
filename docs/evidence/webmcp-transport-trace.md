# WebMCP Transport Trace

`webmcp-transport-trace.json` (in this folder) is a captured run of the real
WebMCP chain through `document.modelContext`. It is regenerated by:

```bash
npm run eval:webmcp   # runs tests/eval/transport-trace.spec.ts + the benchmark
```

## What it proves

| Field | Meaning |
|---|---|
| `transport` | Whether the run used a native `document.modelContext` or the A11yMCP spec-compatible polyfill (`lib/webmcp/polyfill.ts`). |
| `toolNames` | Tools returned by `document.modelContext.getTools()`. |
| `toolOrigins` | Origin tag per tool (`a11ymcp-polyfill` or `native`). |
| `readOk` | `executeTool("get_accessibility_capabilities")` returned a structured result. |
| `badSchemaRejected` | `executeTool("search_products", { evil: "payload" })` was rejected by the strict schema (`additionalProperties:false`). |
| `consequentialRejected` | `executeTool("place_order", { confirmation:false })` was rejected by the consequential gate. |
| `commerceToolsUnregisteredOnUnmount` | After navigating away from the storefront, `getTools()` no longer lists `place_order` / `search_products` — task-scoped `unregisterTool` fired. |
| `coreToolsStillRegistered` | Discovery/audit/negotiation/verification tools remain after unmount. |

## Native vs polyfill

WebMCP is not yet in a stable browser. Rather than gate the whole demo on a
flag, A11yMCP ships a polyfill implementing the W3C draft's imperative
surface (`registerTool` / `unregisterTool` / `getTools` / `executeTool` /
`toolchange`). Every code path — `/demo`, `/inspector`, the guided agent, the
benchmark — dispatches through `document.modelContext.executeTool`. When a
browser provides a native implementation, `ensureModelContext()` detects it
and never installs the polyfill, so the exact same app runs on the real
transport with no code change. `/inspector` shows which is live.
